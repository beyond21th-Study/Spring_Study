# 6.7 애노테이션 트랜잭션 속성과 포인트컷

- 기본적인 트랜잭션 속성은 포인트컷 표현식으로 일괄 적용하는 방식이 대부분의 경우에 잘 맞는다. <br> 하지만 클래스나 메서드마다 서로 다른, 세밀하게 튜닝된 트랜잭션 속성이 필요한 경우에는 이 방식이 적합하지 않다. 이런 경우엔 포인트컷과 어드바이스를 계속 추가해야 해서 설정이 복잡해진다.
<br> 그래서 스프링은 패턴 기반 일괄 설정 대신, 각 메서드(타깃)에 트랜잭션 속성을 직접 지정하는 애노테이션 방식을 제공한다. <br> 이를 통해 더 세밀하고 유연하게 트랜잭션을 제어할 수 있다.

## 6.7.1 트랜잭션 애노테이션

- @Transactional은 스프링에서 트랜잭션 속성을 선언적으로 지정하기 위한 애노테이션이다. 코드가 단순하고 직관적이어서 이해하기 쉽다.
- @Transactional은 다음에 적용할 수 있다: 메서드, 클래스, 인터페이스. 애노테이션이 붙은 객체는 스프링이 자동으로 트랜잭션 적용 대상(타깃)으로 인식한다.
- @Transactional은 다음과 같은 메타 애노테이션을 사용한다:
  - @Target(METHOD, TYPE) → 메서드/클래스에 사용 가능
  - @Retention(RUNTIME) → 런타임에도 유지
  - @Inherited → 상속 가능
  - @Documented → Javadoc에 포함
- 트랜잭션의 모든 속성을 애노테이션으로 설정할 수 있다: propagation (전파 방식), isolation (격리 수준),
<br> timeout (타임아웃), readOnly (읽기 전용 여부), rollbackFor / noRollbackFor (롤백 조건). 기본값이 설정되어 있어서 필요한 것만 선택적으로 지정하면 된다
- @Transactional은 단순히 트랜잭션 속성만 정의하는 것이 아니라, 포인트컷 자동 등록 역할도 수행한다.
- 스프링은 TransactionAttributeSourcePointcut을 사용해서 애노테이션이 붙은 모든 객체를 자동으로 찾아 트랜잭션을 적용한다.

### 트랜잭션 속성을 이용하는 포인트컷

- @Transactional을 사용하면 포인트컷 지정 + 트랜잭션 속성 설정을 애노테이션 하나로 동시에 할 수 있다.
<br> 기존에는 메서드 이름 패턴으로 포인트컷 지정하고 XML이나 설정 파일로 트랜잭션 속성을 관리하는 식으로 분리 되어있었는데
<br> @Transactional을 쓰면 각 메서드별로 다른 트랜잭션 속성을 직접 지정할 수 있어서 훨씬 유연하고 세밀한 제어가 가능해진다.
- 다만, 모든 메서드에 같은 애노테이션을 반복해서 붙이면 코드가 지저분해질 수 있다는 단점도 있다.

<img width="611" height="172" alt="image" src="https://github.com/user-attachments/assets/ee4a13b6-8061-4ff6-a309-2c158181459a" />

- 위 그림은 애노테이션 기반 트랜잭션 처리 구조를 보여주는데,
- <br> 개발자가 메서드에 @Transactional 붙이면 스프링이 해당 메서드를 포인트컷 대상으로 인식한다.
  <br> 애노테이션에서 트랜잭션 속성 읽rh TxInterceptor가 트랜잭션 처리 수행한다.
- 즉 애노테이션 하나로 대상 선정과 트랜잭션 설정, 그리고 적용이 모두 자동화된다.

### 대체 정책

- 스프링은 트랜잭션 속성을 결정할 때 4단계 fallback(대체)순서로 @Transactional을 찾는다.
- 적용 순서 : 타깃 메서드 -> 타깃 클래스 -> 선언 메서드 (인터페이스 메서드) -> 선언 타입 (인터페이스 타입)
- 가장 먼저 발견된 애노테이션의 속성이 적용된다. 끝까지 없으면 트랜잭션은 적용되지 않는다.
- 그렇다면 왜 이런 정책이 필요할까?
  - 공통 속성은 클래스 및 인터페이스 레벨에 두고 예외적인 메서드는 메서드 레벨에 두면
    <br> 중복은 줄이고 세밀한 제어가 가능하다. 또한 유지보수가 쉽다.

## 6.7.2 트랜잭션 애노테이션 적용

- @Transactional은 세밀한 설정이 꼭 필요할 때만 쓰는 게 아니라 직관적이고 간단해서 기본 트랜잭션 적용 용도로도 많이 사용된다.
- 다만 남용하면 어떤 메서드에 트랜잭션이 걸렸는지 파악하기 어렵고 실수로 빠뜨려도 눈치채기 힘들다.
- 그래서 명확한 사용 정책과 코드 리뷰가 중요하다.

<img width="613" height="182" alt="image" src="https://github.com/user-attachments/assets/b54e5485-c75c-4561-b88d-7a896c5c2ab7" />

- 위 그림을 애노테이션 방식으로 바꾸면:
  - 공통 속성 -> 타입(인터페이스/클래스) 레벨
  - 예외 메서드 → 메서드 레벨 . 이렇게 나눠 적용한다.

- <img width="682" height="361" alt="image" src="https://github.com/user-attachments/assets/0c8c42ec-403b-419e-8f55-78d906a41f62" />

```
@Transactional
public interface UserService
```
- 모든 메서드에 기본 트랜잭션 속성 적용, XML의 <tx:method name="*"/> 역할


```
@Transactional(readOnly = true)
User get(String id);

@Transactional(readOnly = true)
List<User> getAll();
```
- XML의 <tx:method name="get*" read-only="true"/> 를 애노테이션으로 바꾼 것. 
- 메서드 레벨이 타입 레벨보다 우선

<img width="661" height="179" alt="image" src="https://github.com/user-attachments/assets/4ed186a8-b8c7-427b-9009-2832daa77d98" />

- 위 그림은 타깃 클래스에 @Transactional 붙였을 때인데,
- 그 결과 클래스 레벨이 인터페이스보다 우선하고 모든 메서드가 기본 트랜잭션 속성 사용한다. 인터페이스에 설정한 readOnly=true 무시됨
- 그래서 getAll()의 읽기전용 테스트가 실패된다.

- 즉, 공통 트랜잭션은 타입 레벨, 예외는 메서드 레벨로 설정하고, 우선순위 충돌에 주의해야 한다.


# 6.8 트랜잭션 지원 테스트
## 6.8.1 선언적 트랜잭션과 트랜잭션 전파 속성

- 트랜잭션 전파 속성(Propagation)은 이미 시작된 트랜잭션이 있을 때 새로 시작할지, 기존 것에 참여할지를 결정하는 규칙이다.
- 가장 기본 전파 속성은 REQUIRED인데 기존 트랜잭션이 있으면 참여하고, 없으면 새 트랜잭션을 생성한다. 
- 이 덕분에 큰 비즈니스 작업 안에서 작은 기능(예: 사용자 등록)을 같은 트랜잭션으로 묶어서 처리할 수 있다.
- 그 결과, 코드 중복이 제거되고 유지보수가 쉬워지며 데이터 정합성이 보장된다.

- 예를 들어보자.
- 1. UserService.add()의 기본 전파 속성이 REQUIRED이다. 
- 단독 호출하면 새로운 트랜잭션 시작되고, 다른 서비스에서 호출하면 기존 트랜잭션에 참여한다.
- 2. EventService.processDailyEventRegistration()는 하루치 이벤트 신청을 한 번에 처리하는 큰 작업 단위이다. 
- 내부에서 UserService.add() 호출하면 add()는 새 트랜잭션을 만들지 않고 기존 트랜잭션에 참여한다. 
- 만약 전파 속성이 없었다면? -> add()가 항상 자기 트랜잭션을 생성되고 큰 작업과 분리된다.
  <br> 결국 코드가 복사되고 중복이 생겨 오류 위험이 증가된다.


<img width="392" height="162" alt="image" src="https://github.com/user-attachments/assets/07351f6d-83f9-4342-bb6c-0ac8fd58a6f0" />

- processEventRegistration()에서 이미 트랜잭션이 시작된다. 
- 그 안에서 add() 호출한다. add()는 REQUIRED 속성을 가지고 있다. 
- 기존 트랜잭션에 그대로 합류되고 하나의 큰 트랜잭션으로 처리된다.
- 그 결과, 중간에 예외 발생하더라도 add()에서 등록한 사용자도 함께 롤백되고 데이터 일관성이 유지된다. 


## 6.8.2 트랜잭션 동기화와 테스트

- AOP와 스프링의 트랜잭션 추상화 덕분에 다양한 데이터 접근 기술을 하나의 트랜잭션으로 묶어 선언적으로 관리할 수 있다
(선언적으로? -> 선언적(declarative)” 이라는 건 “트랜잭션을 어떻게 구현할지를 코드로 직접 쓰는 게 아니라,
의도만 선언해 두면 프레임워크가 알아서 처리해 준다” 라는 뜻이다)

### 트랜잭션 매니저와 트랜잭션 동기화

- 스프링의 트랜잭션 추상화는 PlatformTransactionManager와 트랜잭션 동기화를 통해
<br> 데이터 접근 기술과 상관없이 일관된 트랜잭션 제어를 가능하게 한다.
- 트랜잭션 동기화 덕분에 현재 진행 중인 트랜잭션 정보를 저장소에 보관할 수 있고
  <br> 여러 DAO가 같은 트랜잭션을 공유할 수 있으며 전파 속성(REQUIRED 등)도 정상 동작할 수 있다. 
- 일반적으로는 AOP 기반 선언적 트랜잭션(@Transactional) 이 가장 편리하며, 특별한 경우에만 트랜잭션 매니저를 코드에서 직접 사용한다.

<img width="414" height="147" alt="image" src="https://github.com/user-attachments/assets/3924214b-db95-4290-abbf-edc7dafd8b2d" />


- 이렇게 세 메서드를 순서대로 호출하면, 각 메서드는 REQUIRED라는 전파속성을 가지고 있고 기존 트랜잭션이 없으므로
<br> 각각 새로운 트랜잭션이 생성된다. 총 3개의 트랜잭션이 만들어진다. 즉, 메서드 호출 단위로 트랜잭션이 시작되고 종료된다.


### 트랜잭션 매니저를 이용한 테스트용 트랜잭션 제어

- 테스트 코드에서 여러 서비스 메서드가 각각 새 트랜잭션을 만들지 않고, 하나의 트랜잭션으로 묶어서 실행하고 싶다면 테스트에서 트랜잭션 매니저로 트랜잭션을 미리 시작하면 된다.
- 그러면 REQUIRED 전파 속성을 가진 모든 메서드는 이미 시작된 트랜잭션에 참여하게 된다.

<img width="439" height="227" alt="image" src="https://github.com/user-attachments/assets/c49d984d-e8de-46f3-9a21-d45402950452" />

- 이렇게 호출하면 각 메서드가 각자 트랜잭션 생성해서 총 3개의 트랜잭션이 생김
- 이 세 작업을 하나의 작업 단위로 묶고 싶을 때 -> 테스트 코드에서 트랜잭션을 직접 시작한다.


### 트랜잭션 동기화 검증

- 테스트 코드에서 트랜잭션 동기화와 전파 속성(REQUIRED) 이 제대로 작동하는지 검증할 수 있다.
- 테스트에서 트랜잭션을 읽기 전용(readOnly) 으로 시작한 뒤, 쓰기 작업(deleteAll())을 실행하면 예외가 발생해야 한다.
- 이를 통해 서비스 메서드와 DAO가 테스트에서 시작한 트랜잭션에 실제로 참여하고 있음을 확인할 수 있다.
- 또한, 같은 방식으로 롤백(rollback) 이 정상적으로 적용되는지도 검증할 수 있다.


<img width="643" height="245" alt="image" src="https://github.com/user-attachments/assets/094dec62-8c34-4e7b-900c-b0a4e555d910" />

- 그림설명을 해보자면, 트랜잭션을 읽기 전용으로 시작한다. deleteAll()은 쓰기 작업이다. 
- 이미 시작된 트랜잭션에 참여하므로 읽기 전용 제약 위반 예외 발생한다. 
- deleteAll()이 테스트에서 시작한 트랜잭션에 참여하고 있다는 증거이다.


<img width="635" height="204" alt="image" src="https://github.com/user-attachments/assets/b3b0b313-283b-44a2-b8f5-aaf6e17ca867" />

- JdbcTemplate도 트랜잭션이 있으면 자동 참여된다. 서비스가 아니라 DAO를 직접 호출해도 동일한 예외가 발생한다. 
- 트랜잭션 동기화는 서비스/DAO 계층 모두에 적용된다. 


<img width="672" height="445" alt="image" src="https://github.com/user-attachments/assets/111bfefa-cdad-467b-aa96-eb6093964a0b" />

- 트랜잭션 시작 -> 사용자 2명 등록 > 강제 롤백 -> DB 상태가 원래대로 복구됨
- add()도 테스트 트랜잭션에 참여했기 때문에 롤백의 영향을 받는다. 


### 롤백 테스트

- 롤백 테스트는 테스트 중 수행된 모든 DB 작업을 하나의 트랜잭션으로 묶고, 테스트가 끝나면 무조건 롤백해서
<br> DB 상태를 원래대로 복구하는 테스트 방식이다.

- 왜 필요할까?
- DB를 사용하는 테스트는 테스트가 끝난 뒤 데이터가 변경된다. 그리고 다음 테스트에 영향을 주기 때문에
  <br> 실행 순서에 따라 결과가 달라질 수 있음
- 특히 deleteAll() 같은 메서드는 기존 테스트용 데이터를 전부 날려버린다. 그래서 잘 준비해둔 공통 테스트 데이터가 망가진다. 

- 롤백 테스트의 효과
- 롤백 테스트를 사용하면 테스트 중 추가/삭제/수정한 데이터가 전부 취소된다. 
- 테스트 전 상태로 완전히 복구가 되고 테스트 간 영향이 없다. 
- DB 초기화 작업이 거의 필요 없고 여러 개발자가 같은 테스트 DB를 써도 안전

- 그림을 설명해보자면 테스트 중 모든 작업은 하나의 트랜잭션으로 묶인다.
- 테스트가 종료되면 무조건 롤백
- DB는 변경되지 않음

## 6.8.3 테스트를 위한 트랜잭션 애노테이션

- @Transactional 애노테이션은 서비스뿐 아니라 테스트 클래스와 메서드에도 적용해 트랜잭션 기반 테스트를 쉽게 만들 수 있다.

### @Transactional

- @Transactional 애노테이션은 테스트 클래스나 테스트 메서드에도 적용할 수 있으며, 테스트 실행 전 자동으로 트랜잭션을 시작하고
<br> 테스트가 끝나면 종료(보통 롤백)되도록 만들어 테스트 내 모든 DB 작업을 하나의 트랜잭션으로 묶어준다.

- 테스트에 @Transactional을 쓰는 이유
- 기존 방식dms TransactionManager로 직접 트랜잭션 시작/종료 코드 작성해서 코드가 길고 번거로웠다. 
- 애노테이션 방식:
- 
```
@Test
@Transactional
public void transactionSync() {
    userService.deleteAll();
    userService.add(...);
}
```
- 애노테이션 하나로 동일한 효과를 볼 수 있고 테스트가 훨씬 간결해진다.

- 테스트 트랜잭션의 특징:
  - 테스트 메서드 실행 전에 트랜잭션 시작
  - 메서드 종료 시 트랜잭션 종료
  - 내부에서 호출한 deleteAll(), add() 등은 모두 같은 트랜잭션에 참여한다.
 
- 트랜잭선 속성도 지정 가능하기 때문에 이를 통해 트랜잭션이 실제로 적용됐는지 검증을 할 수 있다.
- 또한 클래스 레벨 적용도 가능하다. -> 클래스 내 모든 테스트 메서드에 트랜잭션 적용할 수 있고
  <br> 메서드에 따로 속성을 주면 메서드 설정이 우선된다. 


### @Rollback

- 테스트에 @Transactional을 적용하면 테스트가 끝난 뒤 자동으로 롤백되는 것이 기본 동작이다.
- 즉, 테스트 중 수행된 모든 DB 작업은 DB에 남지 않는다.

- 왜 자동 롤백이 기본인가? -> 테스트 목적은 기능 검증을 하고 DB 상태를 깨끗하게 유지하기 위함이다.
- 그래서 스프링은 테스트용 @Transactional에 기본적으로 강제 롤백 설정을 해 둔다.

- 롤백을 원하지 않을 때: @Rollback(false)를 쓰면 -> 트랜잭션은 적용되지만 테스트 종료 시 커밋되고 DB에 데이터가 실제로 저장됨

### @TransactionConfiguration

- @Transactional은 클래스 레벨에 적용 가능하고 @Rollback은 메서드 레벨에만 적용 가능하다. 
- 테스트 클래스 전체에 공통 롤백 정책을 적용하고 싶을 때 @TransactionConfiguration을 사용한다.



```
@TransactionConfiguration(defaultRollback = false)
```

- 기본값을 커밋으로 설정하면 롤백이 필요한 메서드만 @Rollback으로 따로 지정된다.


- 왜 필요할까? -> 테스트 클래스에 모든 테스트는 트랜잭션 적용된다. 
- 대부분은 커밋되고 일부 테스트만 롤백된다. 
- 이런 정책을 쓰고 싶을 때 매번 @Rollback(false)를 메서드마다 쓰는 건 번거롭다.
- 그래서 클래스 레벨 공통 설정이 필요함

<img width="473" height="201" alt="image" src="https://github.com/user-attachments/assets/e977ba12-18df-466f-b941-a237856717cf" />

- 위 그림을 보면
- @Transactional -> 테스트 클래스의 모든 메서드에 트랜잭션 자동 적용
- @TransactionConfiguration(defaultRollback = false) -> 기본 롤백 정책을 false로 설정. 즉, 기본은 커밋
- @Rollback -> 특정 메서드만 강제로 롤백

- 결국 @TransactionConfiguration은 테스트 클래스 전체의 기본 롤백 정책을 설정해 주고, @Rollback은 개별 테스트의 롤백 여부를 조절한다.


### NotTransactional과 Propagation,NEVER

- 테스트 클래스에 @Transactional을 적용하면 모든 테스트 메서드가 트랜잭션 안에서 실행된다.
- 그런데 일부 메서드에는 트랜잭션이 필요 없거나 적용되면 안 되는 경우가 있을 수 있다.
- 이럴 때 방법은 두 가지인데
  - @NotTransactional -> 특정 테스트 메서드에 붙이면 클래스 레벨의 @Transactional을 무시하고 트랜잭션 없이 실행된다. 하지만 스프링 3.0부터는 제거 대상(deprecated) 이라 권장되지 않는다.
  - Propagation.NEVER (권장 방식) ->
    ```
    @Transactional(propagation = Propagation.NEVER)
    ```
    - 해당 메서드는 트랜잭션이 있으면 안 된다. 트랜잭션이 존재하면 예외 발생한다.
    <br> 사실상 @NotTransactional과 같은 효과지만 표준적인 방식이라 더 안전하고 권장된다.
- 즉, 테스트 클래스에 @Transactional을 적용했더라도, 특정 메서드에 트랜잭션을 적용하지 않으려면 Propagation.NEVER를 사용하면 된다.

### 효과적인 DB테스트

- DB를 사용하는 통합 테스트는 단위 테스트와 분리해서 별도 클래스로 만드는 것이 좋다.
- 이런 테스트에는 클래스 레벨에 @Transactional을 적용해 롤백 테스트로 만드는 것이 바람직하다.
- 롤백 테스트를 사용하면 각 테스트가 DB 상태에 영향을 주지 않으므로, 테스트들이 서로 독립적이고 자동화하기 쉬워진다.
- 테스트는 실행 순서나 이전 테스트 결과에 의존하면 안 되며, 언제 실행해도 항상 같은 결과가 나와야 한다.
- 트랜잭션과 롤백을 활용한 테스트는 안정적이고 신뢰할 수 있는 DB 테스트를 만드는 데 매우 유용하다.

# 6.9 정리

- 1. 트랜잭션 분리와 DI
  - 트랜잭션 경계 설정 코드를 비즈니스 로직과 분리할 수 있다.
  - 동일한 인터페이스를 구현한 클래스에 DI를 적용하면 클라이언트 수정 없이 트랜잭션 기능을 교체 가능하다.

- 2. 테스트 용이성 향상
     - 트랜잭션처럼 외부 리소스(DB 등) 에 의존하는 코드를 분리하면 비즈니스 로직 중심의 테스트를 만들기 쉬워진다.
     - 목(Mock) 객체를 사용하면 의존 객체도 쉽게 고립 테스트 가능.

- 3. 트랜잭션 = 데코레이터 / 프록시 패턴
     - 트랜잭션 분리는: 1. 데코레이터 패턴 2. 프록시 패턴으로 이해할 수 있다.

- 4. 다이내믹 프록시
     - JDK 다이내믹 프록시를 사용하면 프록시 클래스를 자동 생성할 수 있다.
     - 단, 빈 등록이 번거롭기 때문에 팩토리 빈이 필요하다.

- 5. 스프링의 자동 프록시 생성
     - 스프링은 프록시 팩토리 빈, 자동 프록시 생성기, 포인트컷와 어드바이스 를 통해 프록시를 자동으로 만들어 준다.

- 6. 포인트컷 작성
     - AspectJ 포인트컷 표현식을 사용하면 적용 대상을 편리하게 지정할 수 있다.

- 7. AOP의 역할
     - OOP만으로는 분리하기 힘든 부가기능(트랜잭션, 로깅 등) 을 AOP로 효과적으로 모듈화할 수 있다.

- 8. 트랜잭션 설정 방법
     - 트랜잭션 속성 적용 방식: 포인트컷 표현식, 메서드 이름 패턴, @Transactional 애노테이션

- 9. 테스트에서의 @Transactional
      - @Transactional을 테스트에 적용하면 DB를 사용하는 테스트를 간단하고 안전하게 만들 수 있다.
      - 롤백 테스트, 커밋 테스트 모두 가능.
